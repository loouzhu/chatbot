## 本地运行后端

后端默认连接 `localhost:6379`。启动 FastAPI 前，请先启动 Redis 服务，否则验证码相关接口会报 `ConnectionRefusedError`。

Windows 可安装 Memurai（Redis 兼容服务）并启动其 Windows 服务，或在 WSL 中运行：

```bash
redis-server
```

确认端口可用后，再启动后端：

```powershell
Test-NetConnection localhost -Port 6379
```

输出中的 `TcpTestSucceeded` 应为 `True`。

## 缺陷

以下项目可在单进程、网络与数据库正常、没有并发终态更新的基本聊天验证阶段暂缓。它们仍影响异常恢复、状态一致性或部署能力；完成停止、断连和异常处理验收前，需要重新检查相关项。当前记录来自静态代码检查，尚未通过完整联调验证。

| 待处理项                       | 触发条件与影响                                                                                                                                                                        | 后续处理方向                                                                                               |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| 终态并发更新保护不完整         | 完成、失败与取消更新竞争时，服务层提前修改 Session 管理的 ORM 对象，提交时的自动 flush 可能绕过条件 UPDATE；同时未检查更新是否生效，事件类型可能与实际数据库状态不一致。              | 分离待更新数据与持久化对象，统一使用条件 UPDATE，检查更新结果，并以数据库实际终态构造响应。                |
| 取消保存重试没有恢复事务       | 数据库操作导致事务失效后，继续使用同一个 Session 重试可能持续失败；永久错误也会被重复尝试。数据库正常时不触发。                                                                       | 失败后按事务状态 rollback 或创建独立 Session，只重试可恢复错误。                                           |
| 重复停止与完成后停止不幂等     | 生成任务已清理后，停止接口因注册表中没有任务而抛异常；多个停止请求还可能重复 cancel 同一任务。                                                                                        | 已进入终态时返回实际状态；取消进行中时共享结果，避免重复发起取消。                                         |
| 停止等待没有时间上限           | 模型流关闭或数据库清理长时间不返回时，停止接口会持续等待。                                                                                                                            | 设置有界的等待时间；超时返回“停止处理中”等明确结果，继续跟踪最终状态。                                     |
| 停止请求失败后仍可能显示已取消 | 前端 stopPromise 的 catch 只提示错误并吞掉异常，后续仍执行 abort 并将活动消息标为 cancelled。停止接口成功时不影响正常流程；接口报错或请求失败时，前端状态可能与数据库实际终态不一致。 | 保留停止请求的失败结果，失败时查询服务端实际状态；确认前显示“停止失败”或“状态待确认”，避免直接认定已取消。 |
| 意外断流后的前端恢复不完整     | 未收到终态就遇到 EOF 时被当成正常结束；非主动中断的读取错误会回滚发送前缓存，暂时丢失已显示的部分回答。                                                                               | 记录是否收到终态，异常结束时保留部分内容并查询服务端状态；查询失败时显示状态待确认。                       |
| 取消状态展示与重试入口未完成   | 消息组件没有“已停止”提示，失败消息的重试按钮也没有绑定操作。基本发送和停止请求不依赖这两个入口。                                                                                      | 补充取消状态说明，并实现或暂时隐藏未接通的重试按钮。                                                       |
| 模型客户端资源与超时策略待完善 | 每次生成创建 AsyncOpenAI，但只显式关闭流，未显式关闭客户端；未配置项目自己的连接、读取、整次生成时限和重试策略，目前依赖 SDK 默认行为。                                               | 管理客户端生命周期，显式设置超时与重试，并覆盖长时间无输出的场景。                                         |
| 上游失败事件分类不完整         | 尚未专门处理 response.failed 和 response.incomplete，流结束后可能统一归为流中断，丢失具体失败原因。                                                                                   | 将上游事件转换为明确的本地失败原因，保留部分内容与错误信息。                                               |
| 注册表仅支持单进程             | 多 worker 或多实例部署时，停止请求可能到达未持有生成任务的进程；进程退出后活动消息也没有恢复机制。                                                                                    | 部署扩展前加入跨进程取消路由与遗留活动状态恢复；当前基本验证限于单 worker。                                |

## 边界情况

考虑：

- 历史消息没有超过 Token 限制时，是否完整保留？
- 超出 Token 限制时，是否正确删除较早的消息？
- 是否保留系统提示词？
- 是否保留当前用户消息？
- 是否会出现只保留一半对话轮次的情况？
- 极端情况下，单条消息本身就超过预算怎么办？

测试场景	预期结果
正常生成结束	completed
模型 API 抛出异常	failed
用户主动停止	cancelled
生成过程中客户端断开	按你的断连策略处理
已完成任务再次取消	不应该覆盖 completed
已取消任务再次完成	不应该覆盖 cancelled
